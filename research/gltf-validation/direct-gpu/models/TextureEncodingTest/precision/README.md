# PNG16 core precision investigation

The baseline compiler rejects valid PNG16 before decoding in `ValidatePngPrecision`. Merely removing that guard would still decode to RGBA8888 in both the general color/data route and the packed metallic/roughness route. The latter bakes linear G/B values and material factors into float textures, so its float output alone does not preserve source precision.

The four literal PNG16 fixtures contain adjacent 257/258 values with identical top bytes and unassociated alpha; raw PNG chunk CRCs and decompressed samples were independently verified. `Png16PrecisionTests.Run` expects four linear data decodes and one factor-adjusted metallic/roughness packing case. The grayscale/alpha formats test decoding only, not whether a single-channel image provides all channels required by a given material role. The RGBA/RGB fixtures have B > 0.5, suitable for a normal map's stated positive-Z convention; the RGBA fixture also supplies G/B for metallic/roughness. Source-model and rendered material acceptance are separate gates.

The glTF 2.0.1 material specification explicitly permits metallic/roughness values above eight bits with linear encoding; normal and occlusion are linear roles. Base color and emissive are specified as eight-bit sRGB. No 16-bit sRGB support is claimed or tested here. See <https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#materials>.

`CoreImageMatrixTests.Run` adds independent grayscale transparency, Adam7 RGBA, and progressive JFIF positive decoder examples. Pillow independently reproduced their expected pixels (the JPEG's authored color is lossy and checked within 3 code values). Existing tests cover baseline JPEG, RGBA, and palette4; these controls do not imply complete PNG/JPEG format conformance.

`Png16Prototype` is isolated research code, not the producer. Its initial Skia destination experiments failed; it now uses the model-local managed decoder to serialize linear RGBA32F textures and exercise mips and metallic/roughness factors. `RunPrototype` checks independent literal values. `Png16GpuPrototypeTests` separately tests native linear texture readback and bilinear sampling. These prototype checks are distinguished from the later installed-producer checks below.

The frozen `request.json` requests 12 cases: five current producer, four prototype, and three image-matrix controls. It references only the loaded engine; no replacement producer is compiled. The recorded request references the earlier source freeze; its results are below. The preexisting integration test deliberately expects PNG16 rejection, and must change as part of a future coordinated production fix, not before.

The first guarded attempt reached the editor but helper compilation failed on a `Native` alias conflict; all 12 planned cases were incomplete. Receipt SHA-256 `a641e5bf8de2a1a64e06ddd7e71938b57e22c5fe43029c86bd1ee680050c44f8`. The helper alias was renamed and request re-frozen; no test expectation or producer changed. The successful fixture checks above are not engine evidence.

The corrected baseline receipt SHA-256 `dfcdbdfba16c3e227ae097b4930ae6ab1b7db36038145d58e2b4cbf782ef0d86` executed all 12: the five producer PNG16 cases rejected explicitly, and four Skia RGBA16161616 prototype decodes returned InvalidConversion. Gray+tRNS and Adam7 passed. The progressive JPEG fixture was malformed by a base64 transcription error; its failure is not an engine defect. A newly encoder-generated fixture has independently verified JPEG marker lengths and SOF2; a separate seven-case float decode and image-control request is prepared, unrun.

The second receipt SHA-256 `59cbff37890eeb5f0b75e47a71803d93b584990e51d41c8f455cb108b3ee2a31` executed seven cases: all three corrected PNG/JFIF controls passed, and all four `SKColorType.RgbaF32` requests returned `InvalidConversion`. No cases were incomplete and cleanup was clean. The two tested Skia destination formats are therefore not a demonstrated PNG16 decoder. The local Linux system exposes libpng16, but its presence is not a portable engine dependency or a tested metadata-ignoring decode path; no native core blocker has been proven. RGBA16F alone cannot represent every 16-bit UNORM value exactly. Research must establish a lossless, metadata-ignoring PNG16 decode, bounded mip generation, resource budget, and actual native material sampling before a producer patch can be accepted.

## Managed candidate and production slice

The independently authored matrix exercises all PNG16 color types (0, 2, 4, 6), each of the five PNG row filters, both Adam7 and noninterlaced, split IDAT chunks, grayscale/RGB tRNS, plus CRC, truncation, budget, and trailing-byte rejection. The model-local managed decoder passed **46/46** on the loaded engine; receipt SHA-256 `b367156b832155343b8b62d440b0383b5c2cf645995f9c920703040d544c8f4d`. The isolated float-resource prototype passed **7/7** including independent base/mip and factored metallic/roughness values, and native texture `Load` and bilinear GPU sampling into a float structured buffer; receipt SHA-256 `3b1449e6290fea40965cc6ecfc76bc3d348a9c38e7bd34d0dd5e23400b701bec`. These results are for the candidate, not the installed production compiler.

The integration coordinator granted the narrow production edit after the prototype gate. The new `GltfPng16Decoder.cs` and changes to `GltfTextureCompiler.cs` implement linear PNG16 data and metallic/roughness routes with conservative memory admission; 8-bit/JPEG behavior and 16-bit sRGB rejection remain unchanged. A permanent integration regression is written. At that point production compilation and the actual-producer suite were pending; their later execution is recorded below. Frozen inputs: `production-freeze.json`, SHA-256 `7eb26e463d0a2145211004f77666b1cda2d1efd5765eb0b8fe6d32ce30069378`. The prepared request must only be generated against the newly installed producer and all inputs checked before execution.

The default 256 MiB decoded-byte budget is a working-set bound, not a PNG format limit. The current conservative estimator counts `3 * encoded bytes + 40 * pixel count + 4 * float mip-chain bytes + 1 MiB` before decode. For a 1024x1024 image with mips this is 132,470,080 bytes plus three times the encoded size; for 2048x2048 it is 437,256,192 bytes without mips or 526,734,656 bytes with mips, plus encoded size. Consequently ordinary 2K PNG16 textures can be rejected at the default even though their format is valid. Higher explicitly supplied budgets may admit them, but a public import setting for this policy remains a separate unproven capability. The post-build boundary test checks 1K acceptance and 2K rejection at the default, and 2K admission to the estimator with a 1 GiB budget; this tests admission logic, not actual allocation or rendering of a 2K asset.
